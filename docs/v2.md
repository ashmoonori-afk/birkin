## 0. TL;DR

We adopt 8 ideas from OmO. They split into two tiers:

- **Always-on infrastructure** — cheap, applies to *every* turn:
  **#1 Model Router · #2 Hashline edit · #4 IntentGate · #7 Prompt-Gate · #8 scoped skills**.
- **On-demand heavy cycle** — runs *only* for a complex goal, packaged as a
  separate skill (**Odyssey**), never per turn:
  **Neurosis (plan) · #6 Hyperplan critique · #5 Boulder state · #3 Osiris verify**.

The verifier (#3) is named **Osiris** (judgment/verification). The orchestration
cycle skill is named **Odyssey** *(provisional — rename freely; chosen to avoid
collision with OmO's "Atlas"/"Sisyphus")*. The cycle is **driven by a `goal`
prompt** and is entered only when IntentGate routes there.

## 1. Every turn? No — infra vs. cycle

This is the key decision. The full plan→critique→execute→verify loop is expensive
and must NOT run on every turn. So:

| | runs when | cost | where it lives |
|---|---|---|---|
| **Infra** (#1,#2,#4,#7,#8) | every turn | cheap (routing/editing/gating) | core modules |
| **Odyssey cycle** (Neurosis,#6,#5,#3) | only on a complex goal / `ultrawork` keyword | heavy (multi-agent, loops) | a **skill** (`load_skill('odyssey')`) |

IntentGate (#4) decides per turn: a **simple/normal** turn just runs the agent
(with infra on); a **complex goal** (or the `ultrawork`/`ulw` keyword) hands off
to the **Odyssey** skill with the goal as input.

### 2.1 Approval-gated worker continuation

`worker_hooks.py` is the shared hook contract for work that must stop for human
approval and then continue without another manual kickoff. The proposing worker
stores a versioned, JSON-only continuation beside the action. The handler name
comes from Birkin code (`worker.resume.v1`); a model cannot persist a callback,
import path, command, or new handler. Continuation-bearing work is never
auto-approved, even when its action category is normally on the auto-approve
list.

| worker | runs when | authority ceiling |
|---|---|---|
| **Moirai** | a workflow is explicitly started | provider-portable graph bounded by its declared budget and handlers |
| **Mnemosyne** | memory is indexed, searched, or maintained | mechanical ranking/decay only; no model call |
| **Neurosis** | a request is too ambiguous to execute | interviews and writes a spec; waits for approval rather than guessing |
| **Morpheus** | scheduled review of recent work | emits proposals; does not rewrite the agent directly |
| **Boulder** | a long-running goal is active | persists resumable plan truth; never executes a gate command itself |
| **Harness** | a proposal or turn-boundary review arrives | validates and applies within type/target/budget limits, then appends the rollback ledger |
| **Odyssey** | a goal-completion cycle is started | thin resumable glue around the Boulder plan; owns no execution engine |
| **Osiris** | an Odyssey step claims completion | protocol-only verifier; Boulder remains the persistence authority |

The approval lifecycle is:

```
pending -> approving -> executing -> resume_pending -> resuming -> approved
```

Rejection from `pending` executes neither phase. Action failure records
`failure_stage=action` and never dispatches the continuation. Once the action
succeeds, its receipt is persisted before continuation dispatch; continuation
failure records `failure_stage=continuation`, and another approval cannot replay
the action. The originating worker surface supplies the bounded resume-event
handler. If it is unavailable, the record is not reported as approved.

### 2.2 Durable Moirai input checkpoints

Moirai scripts may request structured human input only from their top-level
orchestration thread:

```python
answer = m.request_answers(
    step_id="deploy-target",
    title="Deploy release",
    description="Choose the deployment target.",
    questions=[{
        "id": "target",
        "text": "Where should Birkin deploy?",
        "options": [{"value": "staging", "label": "Staging"}],
    }],
)
```

The source run enters `waiting_input`. SQLite is authoritative for the binding:
`action_id`, source `run_id`, `worker_id=main`, `step_id`, question digest,
expected actor/capability class, expiry, resume token, input schema version,
and previous-state digest. The pending JSON file is only the channel/WebUI
projection.

Answer acceptance validates every binding and the normalized question schema
under the pending-record lock. A transaction inserts one append-only accepted
answer and changes the wait from `waiting` to `accepted`. Only after that
commit may Birkin update the projection or dispatch a resume. Concurrent or
replayed answers therefore return `reply_rejected`.

A resume starts a child run. Before loading the workflow, Birkin verifies the
stored script hash and previous-state digest, restores the stored args and
bindings, records replay provenance for cached agent calls, and injects a
version-1 answer receipt only when the same step and question contract are
reached. Startup recovery resumes accepted or dispatching waits, and stale-run
reclamation excludes their protected source and child runs.

This is exact logical checkpoint replay, not restoration of an arbitrary
Python call stack. Code before the checkpoint is executed again, so side
effects outside Birkin's durable or idempotent action paths must be replay-safe.
Anonymous parallel thunks have no persistent worker identity and cannot open
input checkpoints.

## 3. The Odyssey cycle skill (goal-driven, on-demand)

Packaged as `skills/automation/odyssey/SKILL.md` (protocol) + a thin runtime
launcher (future). Mirrors how **Neurosis** is skill-as-protocol + thin runtime,
so it is usable today (agent maintains the plan file / verifies inline / spawns
critics via subagents) and gets dedicated runtime as the waves below land.

**Run parameter:** `goal` (the thing to complete). **Goal kickoff prompt** the
launcher feeds the agent:

```
Run the [Odyssey] goal-completion cycle for this GOAL:
  goal: <goal>
Follow it EXACTLY:
 1. If the goal is vague, run the neurosis skill first to a spec.
 2. Draft a CHECKBOX plan (Boulder) at ~/.birkin/boulder/<slug>.json.
 3. Have N adversarial critics (Hyperplan) attack the plan; revise once.
 4. Execute ONE unchecked step at a time. Pick the model by task class
    (quick → haiku, reasoning/architecture → opus). Edit files via
    hash-checked writes (Hashline) only.
 5. After each step, [Osiris] verifies it against the step's acceptance
    criteria — pass → check the box; fail → retry the step (≤ cap).
 6. Stop when every box is checked AND [Osiris] confirms the goal is met.
    Consequential actions (shell/cron) go to the approval queue, never auto-run.
 Report progress as remaining steps, not internals. Resume from the Boulder
 file if interrupted.
```

**When to use Odyssey / when not** (so it never runs per turn):
- USE for a multi-step goal that needs planning + verification ("build X", "migrate
  Y", "refactor Z end-to-end", or the `ultrawork`/`ulw` keyword).
- DO NOT use for a question, a one-file edit, or a quick lookup — those are normal
  turns (infra only). IntentGate enforces this.

## 5. Implementation order (dependency waves)

```
 WAVE 1 ─ foundations (independent · parallelizable)   ┌ gate: unit tests green + review
   ├─ #2 Hashline edit ......... reliability, self-contained
   ├─ #1 Model Router .......... cost/speed, self-contained
   └─ #7 Prompt-Gate + audit ... base that #3/#5/#6 inject through (do BEFORE them)
            │
 WAVE 2 ─ entry + verification                         ┌ gate: tests + adversarial check
   ├─ #4 IntentGate ............ routes turns to modes; gates Odyssey entry
   └─ #3 Osiris verifier ....... uses #1(model)+#7(gate); the "done" primitive
            │
 WAVE 3 ─ on-demand cycle (the Odyssey skill)          ┌ gate: e2e --dry-run
   ├─ #6 Hyperplan critique .... uses #1+#7+subagents; plugs into Neurosis
   ├─ #5 Boulder state machine . uses #3(done-gate)+#4(start-work)+ledger
   └─ Odyssey skill wiring ..... compose Neurosis+#6+#5+#3 behind one goal prompt
            │
 WAVE 4 ─ scoping / hardening                          ┌ gate: security review
   └─ #8 Per-skill scoped perms/MCP .. touches skills+tools+approvals
```

**Why this order:** #7 first (everything injects through it → no rework); #1/#2
independent (immediate value); #3 needs #1 (verifier picks a model); #5 needs
#3 (done-gate) + #4 (entry); #8 last (scope perms after the tool/skill surface is
stable). Morpheus later reuses #5+#3 (nightly = a headless Odyssey run).

## 7. Constraints (non-negotiable)

- **stdlib-only**: Hashline/Router/Boulder/Osiris are all `re`/`hashlib`/`json`/
  `subprocess`-level — no new deps. Borrow OmO's *design*, not its TypeScript code.
- **free**: Router stays within the subscription tier set (`opus`/`sonnet`/`haiku`)
  — no paid-API routing.
- **approval-first**: Osiris verifies but never auto-runs consequential actions;
  cron/shell still queue to `approvals.py`. Odyssey is sandboxed like Morpheus.
