Adapted frontend method

Checklist를 실행 가능한 7개 decision gate로 바꾼다.

각 gate는 입력, 선택지, 측정 기준, 실패 모드, 검증, owner와 revisit trigger를 남긴다. “무엇을 고려할까”에서 “왜 이 결정을 했고 언제 뒤집을까”로 전환한다.

문제와 제약을 고정한다

PRD, 사용자, 기기·네트워크, 규제, 팀 역량, roadmap, happy/edge/failure flow를 명시한다.

행동과 규모를 모델링한다

사용자·QPS·payload·freshness·latency·offline·reconnect·MVP 경계를 수치 또는 범위로 둔다.

route별 delivery와 rendering을 선택한다

CSR, SSR, SSG, streaming, hybrid를 crawlability, personalization, JS cost, cache, 운영비로 비교한다.

contract와 trust boundary를 설계한다

API schema, error, timeout, idempotency, cache, polling/SSE/WebSocket, server-enforced authorization을 분리한다.

ownership, route, state, component를 분해한다

server/URL/durable/ephemeral/form/auth state와 deployment·domain 경계를 먼저 분류한다.

quality attribute를 예산으로 만든다

WCAG, Core Web Vitals, privacy, i18n, browser support, telemetry, security, recovery를 측정 가능하게 한다.

검증·release·evolution을 닫는다

test layers, local/CI parity, artifact provenance, flag, rollout, rollback, production signal과 owner를 정의한다.

Decision record output

Decision Context + constraints Viable options Criteria + evidence Choice + rejected alternatives Consequences + failure modes Validation channel Owner + revisit trigger Rollback signal + recovery path

Debug / programming investigation

Upstream에는 debug lifecycle이 없다.

0
“Debugging”은 Instrumentation 아래의 단일 명사다.

재현, hypothesis, experiment, breakpoint, root cause, regression, manual QA, cleanup 절차는 정의되지 않았다.

Upstream evidence: Instrumentation L266–275. 코드·package·config·test·CI가 없다는 근거는 4-blob tree다.

Birkin-original debug/programming protocol

  1. Reproduce
  2. Pin
  3. Hypothesize
  4. Experiment
  5. Capture RED
  6. Root cause
  7. Smallest fix
  8. Verify
  9. Manual QA
  10. Cleanup

이 절차는 Devkode에 귀속하지 않는다. 업스트림에서 가져온 것은 instrumentation, layered QA, governance, rollback을 고려해야 한다는 coverage seed뿐이다. hypothesis-driven investigation, failing-first proof, real-surface QA와 cleanup은 Birkin 설계다.
